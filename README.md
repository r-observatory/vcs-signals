# vcs-signals

Resolves the source repository behind every CRAN and Bioconductor package (from its DESCRIPTION `URL`/`BugReports`) and collects VCS signals (stars, forks, watchers, issues, pull requests, commits, releases) for repositories on GitHub, and a subset of them for repositories on GitLab and Codeberg (see [Hosts](#hosts)). Data is published daily as SQLite shards attached to a single rolling GitHub release tag (`current`).

## Data Access

```bash
gh release download current \
  --repo r-observatory/vcs-signals \
  --pattern "vcs-signals-summary.db"
```

```r
library(RSQLite)
con <- dbConnect(SQLite(), "vcs-signals-summary.db")

# Top packages by stars
dbGetQuery(con, "
  SELECT package, repo_id, stars, forks, issues_open, trend_30d
  FROM vcs_signals_summary
  ORDER BY stars DESC LIMIT 20
")

dbDisconnect(con)
```

For the full time series, download `vcs-signals-recent.db` (rolling 400-day window) or a per-year `vcs-signals-<YYYY>.db` archive, and query `signals_series(repo_id, date, metric, value)`.

The release also holds `vcs-signals-gitlab-state.db`, the weekly GitLab job's own state. It has one cursor per GitLab host, the last repository that host's rotation read. It is not data to query. Losing it only restarts the rotation from the start of each host's list, and a run that cannot download it says so in a workflow warning.

## Schema

`vcs_signals_summary` carries one row per package: `package, origin, repo_id, stars, forks, issues_open, prs_open, commits_total, releases_total, last_commit_date, license, topics, trend_30d`. `signals_series` is a sparse, change-only time series keyed `(repo_id, date, metric)`.

`last_commit_date` is the committer date of the newest commit on the repository's default branch. `last_release_date` and `last_release_tag` are the publish time and tag of its newest release. On GitHub that is the newest release that is not a draft or a pre-release, so a repository with only pre-releases has a release count and no date. GitLab has no pre-release flag, so there it is the newest release not scheduled for a future date, and the release count leaves scheduled ones out too. Both dates are ISO-8601 instants and are empty when there is no commit or no release. `repo_created_at` is when the repository was created, as its host reports it. It is empty for a repository migrated to Codeberg or mirrored there, since Codeberg reports the day it arrived. A repository the daily run did not reach keeps its previous values. Earlier summaries held the last push to any branch in `last_commit_date` and the day the release count was last seen to change in `last_release_date`; old dated copies keep those values. `median_days_between_releases` is the median gap in days between the days the release count rose, recomputed by the weekly merge.

`top_contributor_commits` is the commit count of the repository's top contributor as the host's contributors list counts it. `top_contributor_bot` is 1 when that contributor is a bot account, 0 when it is a user account, and empty when the contributor is anonymous or has any other account type. GitHub's list gives the account type, so only GitHub rows carry the flag, and it stays empty on GitLab and Codeberg. On Codeberg the count of contributors comes from a clone and is of distinct name and address pairs, so one person who commits under two addresses counts twice. Both are read by the weekly run and kept in `signals_series` as change-only metrics from the first week that read them; GitHub offers no faithful earlier history. `signals_series` holds no empty values: a week that reads a top contributor with no flag empties `top_contributor_bot` in `vcs_signals_summary` and adds no point to the series, where the earlier points stay.

`vcs_signals_summary` and `repo_packages` hold only the packages listed on CRAN or Bioconductor today. `repo_package_links(repo_id, package, origin, first_seen, last_seen)` holds every package-to-repository link the pipeline has seen, including packages that have since been archived and packages whose URL now points somewhere else, so a retired repository's rows can still be traced to the package that led to it. Rows are never deleted, and `last_seen` stops moving once the package no longer resolves to that repository.

The daily run records the days it sees a link. The links from before the table existed were rebuilt from the published copies that survive, dated 2026-08-01, 08-04, 08-09, 08-16, 08-23, 08-30, 09-06, 09-13, 09-14 and 09-15, so a date that came from them is the copy a link appears in rather than the day it began or ended. Such a `first_seen` means "on or before", and 2026-08-01 stands for anything older. Such a `last_seen` means "on or after": the package may have gone on resolving to that repository for up to six more days, until the day before the next copy. A link that began after 2026-09-15 but before the first daily run that kept this table has a `first_seen` of the last run before that one, which is a bound in the same way.

`vcs_dev_tooling` carries one row per scanned GitHub or GitLab repository: the files it keeps (CI configuration, lint and format tools, the documentation site, community files and where GitHub finds them), what its GitHub Actions workflows run, what its `.gitlab-ci.yml` runs, its Pages site, the release items its `.Rbuildignore` leaves out, and the version on its default branch. A column is NULL when the scan did not read its source. `vcs_dev_tooling_rules` states, for every column, where the value comes from and the rule, with the `ruleset_version` each row also carries.

A GitLab repository is read with the same rules as a GitHub one. Files under `.github` on a GitLab repository count as found, though GitLab never runs its workflows, so `ci_github_actions` and the `ci_*` workflow columns there describe files GitLab ignores. The seven `gitlab_ci_*` columns (`gitlab_ci_include`, `gitlab_ci_rcmdcheck`, `gitlab_ci_platforms`, `gitlab_ci_r_devel`, `gitlab_ci_coverage`, `gitlab_ci_site_deploy`, `gitlab_ci_lint`) hold what `.gitlab-ci.yml` runs, read with comments removed, and are NULL on every GitHub repository. When the file includes other configuration with `include:`, a rule its own text does not show reads NULL rather than 0, since the included files may run it. `.gitlab/issue_templates`, `.gitlab/merge_request_templates` and `.gitlab/CODEOWNERS` count as issue templates, pull request templates and CODEOWNERS. `has_pages` on GitLab is 1 when the project has a GitLab Pages deployment. `is_fork` is read on GitLab too, and `parent_name_with_owner` there is the parent's full path on the same host, without the domain. GitLab does not offer the rest, so on a GitLab repository these are NULL: `funding_links`, `owner_sponsorable`, `has_discussions`, `discussions_total`, `homepage_url`, `pages_last_deploy`, `pages_url`, the `site_pkgdown_*` columns unless the repository keeps `docs/pkgdown.yml` (a `gh-pages` build is not read), and `has_pr_template` and `pr_template_source` when the repository has no merge request template of its own, since a group's templates are not visible. `coc_source` and `contributing_source` read `none` when a GitLab repository has no such file.

`gitlab_license(repo_id, license, read_on)` holds the licence the weekly GitLab job last read for each GitLab repository, as the SPDX id GitHub reports, and empty when GitLab reported none or a key with no mapping. `read_on` is the date of that reading. A repository the job has not read has no row, and a week that does not reach it keeps its row. A run that finds the table emptied by a publish from older code restores it from the published summary or its previous copy, or warns that GitLab licences read empty until the next weekly run. `vcs_signals_summary.license` for a GitLab repository comes from this table.

`vcs_repo_owner(repo_id, node_id, owner_login_current, owner_type, owner_node_id, name_with_owner_current, observed_on)` names the current owner of every active GitHub repository, as the daily gauge query returned it on `observed_on`. `owner_type` is `Organization` or `User`, and `owner_login_current` and `name_with_owner_current` are in GitHub's own case. A repository that moved to another account keeps its `repo_id`, which comes from the package's DESCRIPTION URL, and carries its new owner and name, so two `repo_id`s with the same `node_id` are one repository. A row leaves the table when its repository is no longer an active GitHub repository here, or when the query has not returned it for more than 14 days, so a repository with no row has no known owner. The table is a snapshot and keeps no ownership history.

`vcs_repo_name_history(node_id, episode_seq, name_with_owner, owner_node_id, first_seen, last_seen, first_seen_exact, ended_on)` keeps that history from the same daily answer: one episode for each period a GitHub repository kept one name and owner, keyed by its `node_id`. A rename or a transfer closes the open episode with `ended_on` and opens the next, so the change happened after the closed episode's `last_seen` and on or before its `ended_on`. `first_seen_exact` is 0 for a repository's first episode, whose name was already in use when the repository was first seen here, and 1 for an episode a change opened. A repository the answer leaves out keeps its open episode, and rows are never deleted.

## Contents query canary

The weekly AI and repository scan (`ai-weekly.yml`) starts with `Rscript scripts/ai_backfill.R enumerate`, which first sends the contents query for the repositories in `TREE_QUERY_CANARY` (scripts/config.R) as one request. It stops the run when GitHub answers the query with an error, when the request itself fails twice 30 seconds apart (a 502 or a timeout), or when no candidate in a set still shows what it showed on 2026-09-25: four repositories that keep their own code of conduct and contributing guide, and three that inherit their owner's pull request template. A stopped enumerate publishes nothing that week.

To investigate, run `Rscript scripts/ai_backfill.R canary` with `VCS_SIGNALS_TOKEN` set and read each candidate's value in the message. If GitHub changed, fix the query or the parser before the next pass. If the candidates changed their own files, replace them in `TREE_QUERY_CANARY` with repositories that meet the floor today and re-run the enumerate job.

The `gitlab-contents` job has two checks of its own. It stops when at least 20 projects were asked and fewer than half came back, or when fewer than half of those that came back list `DESCRIPTION` at the root. A repository whose files the job cannot process counts as not come back, and is recorded as a failed read with the error's first line. It also stops when the commit message search of `GITLAB_MESSAGE_CANARY` (`gitlab.com/bart-turczynski/punycoder`, a repository with hundreds of commits crediting Claude) finds no commit crediting a tool, so a change in how GitLab matches the search can never record none for every repository. When that repository is not on the roster, its host has no message search, or its search was not read this run, the check is skipped with a warning. A stopped job writes nothing, and the GitHub jobs and the merge go on without it. To investigate, read the job's line for each host and fix the contents query, the parser or `gl_message_regex()`. Then leave the job for next Sunday's run, as the [Hosts](#hosts) section explains.

## Hosts

GitHub, GitLab, Codeberg and Bitbucket are collected daily. `host_predicate(GITHUB_HOSTS)`, `host_predicate(GITLAB_HOSTS)`, `host_predicate(CODEBERG_HOSTS)` and `host_predicate(BITBUCKET_HOSTS)` in `scripts/hosts.R` select the repositories handed to each host's collectors, with the lists set in `scripts/config.R`. The GitHub collectors (node id resolution, daily gauges, weekly, backfill and the AI scan) take only GitHub repositories. GitLab is read through GraphQL on `gitlab.com` and the self-hosted instances listed in `GITLAB_DOMAINS`; `scripts/gitlab.R` resolves project paths to ids and collects the daily gauges, over `scripts/http.R` (requests) and `scripts/pacing.R` (per-host pacing and a request cap). Stars, forks, issues, merge requests (stored as PRs), releases, topics, dates and the archived flag are collected. No mirror flag is read. Watchers, size and owner rows are not collected for GitLab and stay NULL. The daily run does not read GitLab's licence, commit totals or contributors. A path that does not resolve is retried on the next run and never marked gone, since path lookup does not follow renames. `SUPPORTED_HOSTS` only marks which hosts count as supported in `repos.supported`; a repository on any other host keeps NULL signals until a collector for its host exists.

The weekly run (`weekly.yml`, job `fetch-gitlab`, `scripts/gitlab_weekly.R`) reads what the daily run does not. Commit totals for every GitLab repository come over GraphQL. The contributor count, the top contributor's commit count and the licence come over REST, which costs three calls for each repository. GitLab's contributors list counts only a repository's newest 2,000 commits, so on a larger repository the contributor count and the top contributor's commit count cover those commits and not its whole history. Licence keys are mapped to the SPDX ids GitHub reports, and a key with no mapping is empty. The bot flag and the close-time medians stay NULL on GitLab. The REST pass rotates through the repositories of each host and stays within that host's hourly limit: 45 requests on `gitlab.com`, about 15 repositories, and 30 on any other host. When a host's hour is spent, the pass waits for the next UTC hour while the run's 200-minute limit allows. A 429 or `ratelimit-remaining: 0` stops that host for the run. The next run resumes from where the last one stopped, so without a token a full pass can take several weeks. A licence the weekly run reads is kept in a `gitlab_license` table, so the daily run does not publish an empty value over it.

The weekly AI and repository scan (`ai-weekly.yml`) reads GitLab too. Its `gitlab-contents` job reads every GitLab repository's files each week over GraphQL, several projects to a request, without a token, and sends at most `GITLAB_AI_MAX_REQUESTS` (100) requests to one host in a run. It writes the same two files a GitHub scan shard writes, so its rows reach `vcs_dev_tooling` and the AI tables through the same merge. On GitLab 18.4 and later, where GitLab has added a commit message search it marks as experimental, the job also finds commits crediting a tool. On older hosts the commit messages are not searched and those values stay empty, never 0. After the gate, the `gitlab-onsets` job dates each new file from its first commit over REST, without following renames, and each new ignore-file line from the commit that added it, at the same hourly pace as the weekly REST pass, and stops itself at 130 minutes. Commits by a tool's account, author names and merge requests are not read on GitLab. A failed GitLab job never holds back the GitHub jobs or the merge. Leave a failed GitLab job for next Sunday's run: re-running it in the same run also re-runs the gate, every deep shard, `gitlab-onsets` and the merge. A GitLab file the gate or the merge cannot open, or one with an empty key or a value of the wrong type, is left out with a warning, and the GitHub rows publish without it. The merge log says which GitLab files went into that week's data, in a line such as `GitLab partials folded: cheap yes, dev tooling yes, dating no`. When the page cap stops a commit message search before the oldest match, the repository keeps the larger count and the first date its last whole search found.

The GitLab collectors read an optional `GITLAB_TOKEN_<DOMAIN>` environment variable (the domain in upper case, every other character as `_`, for example `GITLAB_TOKEN_GITLAB_COM`) and send it to that host when set. A token raises that host's budget to 500 requests an hour and speeds the pass up. A host that answers 401 loses its token for the rest of the run and is read anonymously. `update.yml` sets none, so the daily run is anonymous, and the `gitlab-contents` job never sends one. Two jobs set one, from the repository secret `GITLAB_TOKEN_GITLAB_COM`: `fetch-gitlab` in `weekly.yml` and `gitlab-onsets` in `ai-weekly.yml`. That secret holds a gitlab.com personal access token with only the `read_api` scope, set 2026-10-19 and expiring 2027-10-18. Renew it before then by creating a new token with the same scope and setting the secret again. A lapsed token only slows the weekly GitLab pass and the dating to the anonymous pace, and nothing fails.

Codeberg is read daily by `scripts/codeberg.R` from Codeberg's anonymous API (`https://codeberg.org/api/v1`), without a token, after GitLab and with 15 minutes of its own. Every request carries the User-Agent `r-observatory/vcs-signals (+https://github.com/r-observatory/vcs-signals)`, and requests start at least one second apart, at most 900 in a run. Codeberg allows 2000 anonymous requests per 600 seconds from one address. The run stops reading Codeberg for the day on a 429, when an answer shows fewer than 400 requests left, or after three failed requests in a row, and every repository it has not read keeps its last values. A repository with a request that fails or gets an answer the run cannot use, such as a server error, a timeout, an unreadable body or a 403, keeps its last values too, rather than publishing part of a row. Besides a success, only two answers are used: a 404 for the newest release, which Codeberg sends when every release is a pre-release, and a 409 for the newest commit, which it sends for an empty repository. Each leaves that value NULL, and the rest of the row is published. The daily run reads stars, forks, watchers, open and closed issues, open, closed and merged pull requests, the release count, the newest release's tag and date, size, topics, the archived flag, the created date and the committer date of the newest commit. Only the first 20 topics are kept, and a repository with more than 500 closed pull requests, merged ones included, has NULL closed and merged pull request counts. Pre-releases are counted as on GitHub: they are in the release count, and the newest release is the newest that is not a draft or a pre-release. The values of a unit the repository has turned off (issues, pull requests or releases) are NULL, and so are its issue values when it uses an external tracker. A repository with releases turned off has a NULL release count even when Codeberg still holds a count for it. The licence stays NULL, since Codeberg reports none and the DESCRIPTION licence is not copied, and so do owner rows and the created date of a repository migrated to Codeberg or mirrored there. A repository is found through its owner's listing, matched by Codeberg's numeric id once it has one, and follows one move on codeberg.org. One that cannot be found is asked again the next day and never marked gone. Once a week `fetch-codeberg` clones each repository's default branch with `--filter=tree:0`, counts its commits (merges included, the count Codeberg's page shows) and its commit identities (distinct name and address pairs over the whole history, with no `.mailmap` and no cap), keeps only the counts, and deletes the clone. Addresses are never stored. The bot flag and the close-time medians stay NULL on Codeberg. The job keeps no state. It stops cloning for the week on a 429, after three failures in a row, or when Codeberg ignores the filter and sends a whole repository. A repository the weekly job does not read keeps last week's values, and a failed Codeberg job never holds back the GitHub weekly publish.

Bitbucket is read daily by `scripts/bitbucket.R` from its anonymous API without a token, after Codeberg and with 5 minutes of its own. Bitbucket allows 60 requests an hour to an address without an account, so a run sends at most 50, one second apart, and each repository takes 6: its object, its forks, its open, merged and declined pull requests, and its main branch. A run reads about 8 repositories, so each one is read about every 4 days, repositories not yet located first. A 429 or three failures in a row stop the run's Bitbucket requests. It reads forks, open, merged and declined pull requests, size, the created date and the date of the newest commit on the main branch. Stars, watchers, issues (Bitbucket removed them in August 2026), releases, the licence, topics, the archived flag and the close-time medians stay empty. A repository not read keeps its last values, one that cannot be found is asked again and never marked gone, and no author data is requested.

A golden record under `tests/testthat/fixtures/golden/` holds the published values for a fixed set of inputs, and `test-golden-parity.R` checks that the scripts still produce them. The publishing workflows skip it on runs from main (`VCS_SKIP_GOLDEN_PARITY=1`), since main's code was checked on push; a dispatch from another branch, a push to main and every pull request check it. To re-record, commit your `scripts/` changes and run `Rscript tests/golden/record.R`, which refuses uncommitted changes under `scripts/`. The commit message of a re-record must name the published value it means to change.

## Caveats

Star history is reconstructed from the GraphQL `stargazers` connection timestamps back to each repository's creation, then maintained forward daily; only the REST list-stargazers endpoint is restricted, not the GraphQL connection. Figures are best-effort, not absolute.
